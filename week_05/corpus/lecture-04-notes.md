# Неделя 4 / Лекция 4 — MCP, инструменты и Tool Orchestration

> Конспект лекции 4. Сведён из транскрибации (`Nueva grabacion 2m4a (2).txt`),
> расширенного PDF-конспекта и скринов презентации. Где формулировки лектора были
> грубыми/устаревшими — взята технически корректная версия (отмечено как **Уточнение**).
> Это теория, не скелет задания (формулировки заданий — в
> [`challenge-tasks.md`](./challenge-tasks.md)).

## Главная мысль

Недели 1–3 учили *управлять моделью изнутри*: промпты и параметры (1), context/memory (2),
state/инварианты/персонализация (3). Неделя 4 — про **выход агента во внешний мир**:
календарь, почта, трекеры, корпоративные базы знаний, код, файловая система, CRM,
внутренние API. Инструмент номер один для этого — **Model Context Protocol (MCP)**.

Базовая проблема: LLM обучена на общих данных и **не знает уникальный контекст**
конкретной компании/проекта/пользователя. Эти знания лежат в Confluence, Git, Jira/
Yandex Tracker, чатах, почте, БД, доменных системах. MCP — стандартный способ подключить
эти источники к AI-приложению.

> **Сквозной тезис недели:** подключить tools — мало. Без state machine, инвариантов,
> валидации и оркестрации (недели 2–3) набор tools быстро превращается в хаотичные
> вызовы. И у любого подхода есть **цена в токенах** — её надо уметь считать.

Связь с циклом из недели 1 (`perception → memory → reasoning → planning → action →
feedback`): MCP/tools достраивают **action** (реальное действие во внешнем мире) и
**perception** (данные из реальных систем как вход), а оркестрация — это **planning** над
набором инструментов.

## 1. Что такое MCP

**MCP = Model Context Protocol** — открытый протокол стандартизированной интеграции
LLM-приложений с внешними источниками данных и инструментами. Удобно понимать как
**универсальный слой подключения** между AI-приложением и сервисами.

Разработан Anthropic (анонс ноябрь 2024), быстро стал индустриальным стандартом.

> **Уточнение (главное заблуждение):** MCP — это **не** конкретный Python/Kotlin/TS-
> фреймворк. Это **протокол/стандарт**. У него есть SDK и реализации на множестве языков
> (Python, Kotlin, TypeScript и др.). Ощущение «MCP = вот эта библиотека на питоне» —
> ошибочно. Путаница ровно из-за обилия реализаций одного стандарта.

### 1.1. Зачем стандарт, если есть API

До MCP агент ходил **напрямую в API каждого сервиса**. Но API у всех разные: разные
форматы ошибок (кто-то отдаёт HTTP 500, кто-то всегда 200 с ошибкой внутри), разные
методы, схемы авторизации, документация. Если писать интеграцию у **каждого агента к
каждому сервису** — это N×M работы.

MCP сводит различия между API и различия между моделями к **одному контракту**:
discovery → schema → call → result. Сервис описывает свои возможности **один раз**, и
любой MCP-совместимый host получает к ним доступ.

> Почему сервисы реально соблюдают MCP (в отличие от «стандартов» REST, которые никто не
> соблюдает): MCP сразу появился во всех крупных нейронках/клиентах. Соблюсти его =
> автоматически попасть во все эти клиенты. Проще соблюсти, чем нет.

### 1.2. Компоненты

| Компонент | Роль |
|-----------|------|
| **MCP Host** | AI-приложение, управляющее одним/несколькими клиентами. Пример: Claude Desktop, IDE, твой агентский backend |
| **MCP Client** | Компонент внутри host, держит соединение с сервером и получает от него возможности/контекст |
| **MCP Server** | Программа, предоставляющая tools/resources/prompts. Локальная или удалённая |
| **LLM** | Модель: получает контекст, выбирает инструмент, интерпретирует результат, формирует ответ |

> **Уточнение:** «MCP встраивается в нейронку» / «LLM сама шлёт HTTP в сервис» — неточно.
> В реальной архитектуре **LLM лишь генерирует намерение** вызвать tool, а сам вызов
> MCP-сервера исполняет **host/client** и возвращает результат модели. Модель напрямую с
> MCP-сервером не общается. На архитектурном слайде это подписано явно: на участках
> `USER/UI` и `HOST (Agent/Client App)` — **No tokens spent**; токены начинают тратиться
> только на `LLM API (sampling calls)`.

## 2. Что MCP-сервер может отдавать (примитивы)

| Primitive | Что это | Пример |
|-----------|---------|--------|
| **Tools** | Исполняемые функции, которые модель может вызвать через host/client | `get_forecast`, `read_calendar`, `create_ticket`, `query_database` |
| **Resources** | Данные/контекст, которые можно **читать** | файл, запись БД, схема проекта, документ Confluence |
| **Prompts** | Переиспользуемые шаблоны взаимодействия | шаблон code review, шаблон анализа инцидента, запрос к CRM |
| **Sampling** | Возможность сервера попросить host/client выполнить **LLM-вызов** | серверу нужен model-independent completion без прямой зависимости от LLM SDK |

**Изоляция возможностей** — ключевой плюс. У сервиса может быть «жирный» API, но через MCP
ты отдаёшь только нужные tools: например `read_calendar`, но **не** `create_event`. Если
write-tool не выставлен — модель физически не сможет ничего создать/удалить.

## 3. Tool schema (на примере погоды)

Чтобы модель поняла, **какой** инструмент существует, **когда** его выбирать и **какие**
аргументы передать — у каждого tool есть схема: `name`, `title`, `description`,
`inputSchema`, `required`. На слайдах показаны два варианта одного и того же погодного
инструмента.

Дискавери идёт обычным JSON-RPC-запросом `tools/list`, в ответ — массив tool-описаний:

```json
// MCP Request
{ "jsonrpc": "2.0", "id": 2, "method": "tools/list" }

// MCP Response
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "tools": [
      {
        "name": "weather_current",
        "title": "Weather Information",
        "description": "Get current weather information for any location worldwide",
        "inputSchema": {
          "type": "object",
          "properties": {
            "location": {
              "type": "string",
              "description": "City name, address, or coordinates (latitude,longitude)"
            },
            "units": {
              "type": "string",
              "enum": ["metric", "imperial", "kelvin"],
              "description": "Temperature units to use in response",
              "default": "metric"
            }
          },
          "required": ["location"]
        }
      }
    ]
  }
}
```

`description` нужен **для построения релевантности**: по нему модель решает, подходит ли
tool под запрос. Плохой description → модель не выберет нужный tool или выберет лишний.

### 3.1. Kotlin SDK: сервер — обёртка над обычным HTTP

В Kotlin-примере из презентации MCP-сервер создаётся через SDK, регистрируется tool, а
внутри обработчика дёргается **обычный HTTP-клиент** к погодному API (api.weather.gov):

```kotlin
// 1. Создаём MCP Server
val server = Server(
    Implementation(name = "weather", version = "1.0.0"),
    ServerOptions(capabilities = ServerCapabilities(tools = ServerCapabilities.Tools(listChanged = true)))
)
// локальный транспорт через stdin/stdout
val transport = StdioServerTransport(System.`in`.asInput(), System.out.asSink().buffered())

// 2. Обычный HTTP-клиент к внешнему API (НЕ MCP)
suspend fun HttpClient.getForecast(latitude: Double, longitude: Double): List<String> {
    val points = this.get("/points/$latitude,$longitude").body<Points>()
    val forecast = this.get(points.properties.forecast).body<Forecast>()
    return forecast.properties.periods.map { /* ...format... */ }
}

// 3. Регистрируем tool: маппинг tooling -> конкретный HTTP-запрос
server.addTool(
    name = "get_forecast",
    description = "Get weather forecast for a specific latitude/longitude",
    inputSchema = Tool.Input(/* latitude:number, longitude:number; required */)
) { request ->
    val latitude = request.arguments["latitude"]?.jsonPrimitive?.doubleOrNull
    val longitude = request.arguments["longitude"]?.jsonPrimitive?.doubleOrNull
    if (latitude == null || longitude == null) {
        return@addTool CallToolResult(content = listOf(TextContent("The 'latitude' and 'longitude' parameters are required.")))
    }
    val forecast = httpClient.getForecast(latitude, longitude)
    CallToolResult(content = forecast.map { TextContent(it) })
}
```

> Самый важный слайд лекции: внутри хендлера tool происходит **маппинг** между tooling
> (то, что дёргает модель) и конкретным запросом к твоему сервису/внешнему API. То есть
> MCP-инструмент сам по себе не магия — это **аккуратная обёртка** над реальным действием.

## 4. Local vs Remote MCP

| Вариант | Как работает | Когда подходит |
|---------|--------------|----------------|
| **Local / STDIO** | Сервер запускается локально, общается через stdin/stdout | локальные файлы, dev-tools, CLI, IDE, доступ к локальному проекту |
| **Remote / HTTP** | Сервер доступен по сети (HTTP-транспорт + авторизация) | корпоративные сервисы, публичные tools, командное/shared-использование |

Для **публичного** сервера нужен развёрнутый backend, домен/URL, HTTPS, авторизация и явно
описанные tools/resources/prompts. Для **локального демо** хватает STDIO-варианта и
локального SDK.

> **Уточнение:** «LLM просто шлёт HTTP-request» — верно только для remote. MCP поддерживает
> разные транспорты; в local это STDIO, не HTTP.

## 5. Стадии работы с MCP-инструментом (и где появляется overhead)

Типовой flow вызова (слайд `STAGES`). Важно понимать **где тратятся токены** — именно тут
рождается главная проблема стоимости.

```
1. User input        — пользователь вводит prompt                 (токены НЕ тратятся)
2. Context collection— host собирает system prompt, developer
                       instructions, profile, state + get tools mcp
3. Sampling call #1  — LLM получает контекст + ВСЮ tool schema,
                       выбирает инструмент(ы) и аргументы          (токены тратятся)
4. Tool calling      — host/client делает JSON-RPC-вызов сервера   (токены НЕ тратятся)
5. Sampling call #2  — результат tool + ВСЕ токены call #1
                       возвращаются в контекст; LLM интерпретирует (токены тратятся)
```

Ключ (видно на слайде): **call #2 включает в себя токены call #1**. На каждый sampling call
в контекст уезжает вся tool schema (список всех tools со всеми описаниями), независимо от
того, нужен один tool или ни одного. Даже на запрос «сколько времени» модель сначала
получает весь список tools.

## 6. Token overhead: почему MCP может быть дорогим

Вторая крупная тема лекции — сравнение MCP с подходом **Skill + CLI**. Тезис: MCP удобен
как стандарт, но **дорог по токенам**, когда tools много, схема большая, а агент делает
много последовательных действий.

### 6.1. Idle cost (из слайда)

```
MCP Server (46 tools)
├── Tool schemas:  ~5 787 токенов
├── Loaded:        ALWAYS (на каждый sampling call)
└── Idle cost:     5 787 токенов даже на "What time is it?"

Skill + CLI
├── SKILL.md:      ~3 760 токенов
├── References:    ~763 токена
├── Bash schema:   ~200 токенов
├── Total:         ~4 723 токена
├── Loaded:        ON DEMAND (только когда нужно)
└── Idle cost:     0 токенов

Schema size delta: ~1 064 токена (НЕ главный фактор)
```

> Сама по себе разница схем (~1k токенов) невелика — **не она** делает MCP дорогим.
> Главный фактор — как растёт расход на серии вызовов (ниже).

### 6.2. Квадратичный рост — главный инсайт (O(N²) vs O(1))

MCP растёт по контексту **квадратично**: на каждый следующий шаг входит **вся предыдущая
история + снова вся схема**. Skill+CLI растёт почти **линейно** — добавляется только длина
вызванного bash-скрипта (CLI-команды исполняются локально, на 0 токенов).

| Actions | MCP tokens | Skill+CLI tokens | Ratio |
|---------|-----------|------------------|-------|
| 2 | 24 361 | 13 506 | 1.8× |
| 6 | 63 269 | 14 826 | 4.5× |
| 10 | 109 857 | 14 546 | 7.6× |
| 15 | 178 892 | 15 196 | 11.8× |
| 20 | 259 927* | 15 846 | 16.4× |

> *На слайде в строке «20» опечатка (`59 927`); сам лектор это оговорил — по прогрессии и
> по ratio 16.4× там ~**259 927**. Привожу исправленное значение.

Разбор расчёта для Skill+CLI (со слайда):

```
System prompt = 1500 токенов
User prompt   = 200 токенов
SKILL.md      = ~3760 токенов (ON DEMAND)
bash schema   = ~200 токенов

Sampling call #1: 5660 input + ~300 output
Local execution: 0 токенов (6 CLI-команд исполняются локально)
Sampling call #2: 6460 input + 200 output
Total: ~12 620 токенов
```

| Подход | Сильная сторона | Слабая сторона |
|--------|-----------------|----------------|
| **MCP** | единый стандарт; remote/shared/public tools; discovery; interoperability | schema/results раздувают контекст; квадратичный рост при частых вызовах |
| **Skill + CLI** | дёшево для локальной автоматизации/dev-workflow; грузится on demand; idle ≈ 0 | нужен локальный CLI/tool; сложнее стандартизировать для внешних/remote |

> **Числа НЕ универсальны.** Они относятся к конкретной реализации (46 tools) и конкретному
> набору инструментов. Чем больше сервер и тяжелее возвращаемые данные — тем сильнее растут
> расходы. Не считать это «законом».

## 7. «MCP становится deprecated» — корректировка

В транскрибации звучит сильное: «MCP становится deprecated». **В учебном контексте это
понимать буквально не нужно.**

> **Корректная формулировка:** MCP **не устарел**. Он по-прежнему полезен для
> стандартизированных **remote/shared** интеграций. Но для **локальной автоматизации,
> тестирования, CLI-команд и тяжёлых итеративных workflow** подход **Skill + CLI** может
> быть заметно дешевле по токенам.

Почему MCP **не отмирает**:
- Skill+CLI требует, чтобы у тебя локально был запущен **CLI-инструмент**. Для удалённого
  сервера это либо не работает, либо надо писать свой CLI-обёртку поверх — что мало кто
  будет делать, **пока токены относительно дёшевы**.
- Для **публичных** tools (другие пользователи не обязаны иметь твой локальный CLI) MCP —
  естественный выбор: подключение через стандартный server interface.

Практический вывод: знать **оба** подхода. Skill+CLI — туз в рукаве для экономии токенов;
MCP — стандарт для shared/remote.

## 8. Минусы и риски MCP (безопасность)

В лекции — «очевидное отсутствие безопасности» с примером **логической бомбы**: в название
встречи зашивают `rm -rf`, сервер исполняет это в shell — и всё стёрто. Лектор сравнивает
будущие массовые атаки с текущим сканом портов: «дёргают все ручки, вдруг открыто».

> **Уточнение:** «MCP без безопасности» — слишком грубо. У протокола есть
> authorization/security considerations. Но tool-доступ **действительно** открывает опасные
> поверхности, и их надо закрывать руками.

| Риск | Что может случиться | Как снижать |
|------|---------------------|-------------|
| **Over-permission** | tool делает больше нужного: читает лишнее, создаёт/удаляет | least privilege: только нужные tools, разделять read/write, требовать confirmation |
| **Prompt injection** | внешний контент заставляет модель вызвать опасный tool | фильтрация, sandbox, explicit allowlist, validation, human confirmation |
| **Command injection** | tool зовёт shell/CLI с неочищенными аргументами (логическая бомба) | не передавать raw input в shell; allowlist команд; escaping; sandbox |
| **Data leakage** | модель получает слишком много приватного контекста | scope, access control, masking, audit logs |
| **Tool result confusion** | tool вернул неожиданный результат, LLM интерпретировала неверно | строгая схема результата, typed responses, post-validation |

Связь с неделей 3: это ровно про **инварианты + validation + статический guard**. Опасное
действие должно ловиться **кодом** (allowlist/least privilege), а не «просьбой в промпте».

## 9. Оркестрация MCP

Внутри **своего агента** (не готового код-ассистента) задача — не «подключить один tool»,
а **оркестрировать набор**. Реальный запрос требует нескольких действий:

```
User query
  → intent detection
  → select relevant MCP tools
  → call tool #1: read calendar
  → call tool #2: read task tracker
  → LLM reasoning over results
  → if destructive action: ASK confirmation   ← guardrail из недели 3
  → call tool #3: create event / update task
  → validate result
  → final response
```

Здесь возвращаются все темы недель 2–3: **state machine, invariants, allowed transitions,
validation, memory**. MCP без stateful-архитектуры = хаотичный набор вызовов.

> Это и есть «supervisor-агент», который в неделе 3 был помечен как задача weeks 4–5:
> теперь оркестратор принимает **содержательные** решения (какой tool, в каком порядке,
> нужно ли подтверждение), а не только двигает FSM.

## 11. Корректировки и технические уточнения (из источника)

| Фрагмент из транскрибации | Корректировка |
|---------------------------|---------------|
| «МСП» | Ошибка распознавания. Правильно: **MCP / Model Context Protocol** |
| «MCP встраивается в нейронку» | Точнее: MCP работает **между host/client и server**. Модель не общается с сервером напрямую |
| «Любая LLM умеет общаться с MCP» | Точнее: нужен **host/client layer**, который превращает tool calls в MCP-вызовы |
| «LLM просто шлёт HTTP-request» | Не всегда. Транспорты разные (local STDIO / remote HTTP); вызов делает host, не модель |
| «MCP без безопасности» | Слишком грубо. Есть authorization/security considerations; но нужны least privilege, sandbox, confirmation, validation, audit |
| «MCP deprecated» | Слишком сильно. Для локальных повторяющихся workflow Skill+CLI дешевле; MCP остаётся стандартом для shared/remote |
| Token-таблицы из слайдов | Демонстрация, не закон. Числа зависят от схемы, числа вызовов, клиента, модели, реализации. В строке «20 actions» — опечатка слайда |

## 12. Дополнения (не из лекции, от ассистента — пометка)

Сверено в сети, июнь 2026. Лекция описывает паттерн «руками» — индустрия уже
стандартизировала большую часть.

### 12.1. Статус и управление MCP

MCP анонсирован Anthropic в ноябре 2024, спецификация — на `modelcontextprotocol.io`. В
**декабре 2025** проект передан в **Agentic AI Foundation** под Linux Foundation (туда же,
куда отошёл `AGENTS.md`). То есть MCP — уже **vendor-neutral** стандарт, а не «протокол
Anthropic». Это аргумент против «MCP умирает»: стандарт институционализирован.

### 12.2. Транспорт = JSON-RPC 2.0

Под капотом MCP — **JSON-RPC 2.0** (видно на скрине 1: `"jsonrpc": "2.0"`, `"method":
"tools/list"`). Два официальных транспорта:
- **STDIO** — локальные серверы (stdin/stdout).
- **Streamable HTTP** — remote (заменил старый HTTP+SSE транспорт в spec 2025-03-26).

Полезно знать для отладки: на проводе это обычные JSON-RPC `request/response/notification`.

### 12.3. Откуда «MCP deprecated»: Code Mode / code execution

> **Флаг: интерпретация.** Тезис лектора почти наверняка опирается на две вещи 2025 года:
> **Anthropic «Code execution with MCP»** (ноябрь 2025) и **Cloudflare «Code Mode»**. Идея:
> вместо того чтобы загружать **все** tool-схемы в контекст и гонять много sampling call,
> модель **пишет код**, который вызывает tools программно (loop/filter/batch на стороне
> кода), а в контекст возвращается только итог. Это и убивает квадратичный рост — ровно то,
> что в лекции названо «Skill + CLI». Так что «MCP deprecated» = «naive tool-calling по
> каждому tool дорог», а не «протокол мёртв».

### 12.4. Claude Skills

«Skill» в лекции = **Agent Skills**, которые Anthropic зарелизила (Claude Skills, октябрь
2025): папка со `SKILL.md` + скрипты/ресурсы, **подгружается on demand** (progressive
disclosure). Отсюда «idle ≈ 0 токенов»: пока скилл не нужен — он не в контексте. Это и есть
причина выигрыша по токенам против always-loaded MCP schema.

### 12.5. Привязка к нашему репозиторию

- Наш `shared/client.py` уже умеет OpenAI-совместимый payload — MCP-слой ляжет **поверх**

### 12.6. Official Python SDK

Для MVP — официальный `mcp` Python SDK (`uv add "mcp[cli]"`) с `FastMCP`: декоратор `@tool`,
запуск STDIO/Streamable HTTP из коробки. Это минимальный путь к демо без ручного JSON-RPC.
(Ask before heavy deps — но `mcp` тут профильная зависимость недели.)
