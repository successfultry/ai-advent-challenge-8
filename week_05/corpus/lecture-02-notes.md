# Неделя 2 / Лекция 2 — Внутренности агента: context, memory, planning, tools

> Конспект лекции 2. Сведён из транскрибации (`Nueva grabacion 4m4a.txt`) и
> расширенного PDF-конспекта. Это теория, не скелет задания (формулировки заданий —
> в [`challenge-tasks.md`](./challenge-tasks.md)).

## Главная мысль

Неделя 1 была про *как спрашивать LLM* (промпты, параметры, выбор модели). Неделя 2 — про
*как построить управляемого агента*. Фокус смещается с одиночного запроса на **внутреннюю
инженерию агента**: как он удерживает контекст, хранит память, строит план и вызывает
инструменты.

Сквозной тезис: разработчик делегирует агенту не микродействия, а **законченные этапы**.
Для этого агенту нужны четыре управляемых блока — без них он «плавает в мировой базе
знаний» и галлюцинирует.

> Важно понимать: при обычном **inference веса модели не меняются**. Когда говорят
> «модель подстроилась под диалог» — на самом деле меняется *распределение вероятностей
> следующего токена* из-за нового контекста, истории и system-инструкций, а не сами веса.
> Поэтому всё «обучение на лету» в рамках сессии — это управление **контекстом**, а не
> переобучение модели.

Связь с циклом из недели 1 (`perception → memory → reasoning → planning → action →
feedback`): четыре блока ниже — инженерные компоненты *вокруг* этой цепочки.

| Блок | За что отвечает |
|------|-----------------|
| **Context management** | что модель видит *прямо сейчас* в контекстном окне |
| **Memory management** | что сохраняется *между* шагами/сессиями и как возвращается в контекст |
| **Planning** | превращение цели в план, задачи, стратегию, перепланирование |
| **Tool orchestration** | выбор и вызов tools, интерпретация результата, обработка ошибок, обновление state |

## 1. Context management

### 1.1. Почему контекст критичен

Базовая LLM **не знает, что ты строишь**, пока не сказано. Она обучалась на огромном
корпусе, но конкретный проект, стек, архитектура, правила репозитория и текущий статус
работы должны быть **явно поданы** в контекст.

Коммерческие ассистенты частично делают это сами (индексируют проект, подтягивают
историю, хранят preferences). Но если строишь своего агента или настраиваешь
code-assistant — эту механику надо понимать и контролировать.

> **Главное практическое правило:** если агент делает странные вещи — проверяй сначала
> **контекст, а не модель**. Чаще проблема не в «тупой нейронке», а в грязном, слишком
> широком или противоречивом контексте.

### 1.2. Роли и инструкции

Роль задаёт рамку: кто агент, какую задачу решает, какие ограничения соблюдает, в каком
формате отвечает. Не замена контексту, но сильный способ **сузить пространство решений**.

- Плохо: «Напиши код.»
- Нормально: «Ты senior Python backend engineer. Стек FastAPI + SQLAlchemy 2.0 +
  PostgreSQL. Соблюдай архитектуру, не меняй публичные контракты без необходимости,
  добавляй тесты, перед изменениями составь план и перечисли файлы, которые тронешь.»

> Роль/инструкции сужают пространство решений *в дополнение* к сэмплингу: модель и так
> выбирает следующий токен не из всей матрицы, а из усечённого распределения (top_p /
> top_k) — механика выбора токена разобрана в неделе 1 (§8). Инструкции сужают *что*
> вообще релевантно, сэмплинг — *как* выбирается токен из релевантного.

### 1.3. Техники управления контекстом

Все техники решают одну проблему: **контекстное окно конечно**, а информации больше, чем
влезает. Разница — *что* выкинуть/сжать/подмешать и *по какому критерию*.

| Техника | Механика (как это работает) | Когда брать | Риск |
|---------|----------------------------|-------------|------|
| **History compression** | Когда история разрослась — отдельным запросом к LLM делаешь summary прошлых сообщений и заменяешь их одним сжатым блоком. Дальше диалог идёт от summary, а не от полной истории. | окно почти заполнено, но диалог нужно продолжать | summary делает LLM → теряет детали, числа, edge cases; может исказить договорённости |
| **Sliding window** | Держишь только последние N сообщений, старые механически отбрасываешь (без сжатия). Простейшая стратегия, без затрат на LLM. | разговор крутится вокруг одной темы, ранние детали уже не нужны | если в одном чате смешаны разные задачи — выкинешь нужное из начала |
| **Vector retrieval (RAG)** | Документы/факты заранее режешь на chunks, превращаешь в embeddings, кладёшь в vector store. На каждом запросе ищешь top-k близких по смыслу chunks и подмешиваешь только их текст. | большие базы знаний, документация, большой репозиторий — всё не влезает в окно | retrieval вернёт нерелевантные chunks; даже верные факты не гарантируют верный вывод |
| **Context layers** | Контекст делишь на слои по приоритету (правила проекта / фича / задача / временное состояние) и в каждый запрос подмешиваешь только нужные слои. | большие проекты, разным агентам/шагам нужны разные части | трудно правильно разложить знания по слоям и поддерживать актуальность |
| **Clear / recreate dialog** | Полностью чистишь контекст и начинаешь с чистого system prompt. Важные договорённости переносишь руками. | задача принципиально новая или чат «загрязнён» мусором прошлых попыток | можно потерять важное, если забыл перенести явно |
| **Token pruning** | Точечно удаляешь из контекста мусор: длинные логи, повторы, неактуальные tool-результаты. | длинные агентные циклы, где копится шум | слишком агрессивная обрезка вырежет важный нюанс |
| **Topic branches** | Разные темы ведёшь в отдельных ветках/субконтекстах (backend отдельно, frontend отдельно), потом сводишь. | параллельно идут несколько направлений в одном проекте | нужна оркестрация, иначе ветки начнут противоречить друг другу |

Практические ориентиры:
- **Дёшево и просто** → sliding window / clear dialog. Не требуют LLM-вызовов.
- **Длинный диалог по одной теме** → history compression (но сохрани точные факты отдельно).
- **Много документов/кода** → vector retrieval. Единственное, что масштабируется.
- **Большой долгий проект** → context layers + retrieval вместе.

> **Осторожно с провайдерским авто-триммингом:** некоторые шлюзы (OpenRouter) сами режут
> контекст при переполнении — тогда не увидишь, «что ломается», т.к. обрезку замаскировал
> провайдер. Для честного эксперимента это отключают или берут прямой API.

Хороший запрос обычно содержит: **язык, стек, цель, ограничения, релевантные файлы,
критерии готовности, формат результата, правила проверки.**

### 1.4. Масштаб окна: почему оно кончается быстро (особенно на коде)

Базовое определение `context window` и его размер (заявленные 10М «не работают», реально
**~1 млн токенов**) — в неделе 1 (§5 glossary, §10). Здесь важна дельта для код-агента:

- одно взаимодействие по **код-задаче ≈ 8 000–10 000 токенов** (код жрёт токены);
- окно в **1 млн ≈ ~100 таких сообщений**;
- даже с обрезкой/топиками/прунингом длинная сессия быстро упирается в history compression.

Вывод: окно большое, но **не бесконечное**. Для код-агентов управление контекстом
проектируют **заранее**, а не когда окно уже переполнилось.

## 2. Memory management

Это **не «магическая память модели»**, а конкретная инженерная система: summary,
JSON-файлы, БД, vector store, правила, preferences, project state. Память живёт **снаружи**
модели; в контекст она лишь подгружается при необходимости.

> Граница с context management: *context* — что подаётся в окно **сейчас**; *memory* — что
> хранится **между** запросами и откуда context потом собирается.

### 2.1. Три уровня памяти

| Тип | Что значит | Пример |
|-----|-----------|--------|
| **No memory** | каждый запрос независим, модель знает только текущий prompt | одноразовый REST-запрос без истории |
| **Session memory** | история внутри текущего диалога / agent run | модель видит предыдущие сообщения чата |
| **Long-term memory** | данные сохраняются *вне* модели и подгружаются в будущие сессии | файлы состояния, user profile, vector DB, summaries |

### 2.2. Виды long-term памяти

- **Компрессированная (summary).** Хранить не всю историю, а свёртку: summary этапа/дня/
  задачи/проекта. Плюс: экономит токены, легко. Минус: summary делает LLM → теряет детали
  → потерянное провоцирует галлюцинации. **Хорошо для статуса проекта, плохо для точных
  требований, API-контрактов, edge cases, чисел.**
- **Vector-based.** Факты/chunks как embeddings, поиск по смысловой близости. Рядом с
  embedding — ссылка на оригинальный текстовый chunk (его и подмешивают, embeddings обратно
  в текст не декодируют). Плюс: масштабируется, тянет большую базу знаний. Минус: нужен
  embedding-шаг, retrieval ошибается, факты ≠ верный reasoning.
- **Слоистая (layered).** Знания по уровням приоритета:

  ```
  L1  Global project rules: стек, архитектура, стиль кода
  L2  Feature context: что строим на этой неделе
  L3  Task context: конкретная задача текущего agent run
  L4  Temporary state: что сделано, какие ошибки, какие файлы изменены
  ```

  Мощно для больших проектов, но сложно: надо классифицировать память, обновлять её и
  решать, какие слои подмешивать в конкретный запрос.

  **Как это делают на практике:** диалог сбрасывают в отдельное summary, затем лог разбивают
  на уровни (стратегический / тактический / локальный) — отдельным LLM-запросом, по таймеру
  или по событиям. В Claude это из коробки: глобальный CLAUDE.md → проектный CLAUDE.md →
  локальный контекст = те же слои приоритета.

- **Rule-based.** Правила в явном виде (ближе к экспертным системам / fuzzy logic).
  Пример: «если просят изменить публичный API — сначала предложи план миграции, не ломай
  обратную совместимость без подтверждения». Плюс: контроль, детерминизм, удобно для hard
  constraints. Минус: негибко, надо поддерживать. **Хранить тут запреты, обязательные
  проверки, стиль, требования безопасности.**
- **Self-reflective / semantic.** Хранит не только факты, но и смыслы: стиль, предпочтения,
  паттерны, тон, долгосрочные цели → ассистент кажется «узнающим». Минус: требует
  фильтрации, может закрепить неверные интерпретации. Опасно без механизма обновления/
  удаления памяти.

### 2.3. Память по уровню агента

| Уровень | Что обычно есть | Поведение |
|---------|-----------------|-----------|
| **Basic assistant** | текущий контекст + история сессии | отвечает на текущий запрос, быстро теряет детали в длинном чате |
| **Smart assistant** | session memory + summaries + rules + иногда retrieval | лучше держит задачу, помнит часть предпочтений, меньше путается |
| **Advanced agent** | layered memory + vector retrieval + self-reflection + explicit state | устойчивая рабочая система: помнит проект, план, ошибки, состояние, цели |

## 3. Planning

Стадия, на которой агент не просто отвечает, а **организует работу**. Без планирования
модель хаотично генерирует код и ломает работающие части.

### 3.1. Минимальный planning loop

```
1. Определить цель
2. Уточнить ограничения
3. Разбить цель на задачи
4. Выбрать стратегию исполнения
5. Проверить, что стратегия подходит
6. При необходимости перепланировать
7. Подтвердить план у юзера или перейти к выполнению
8. После каждого шага обновлять state
```

### 3.2. Что содержит хороший план

Цель (результат на выходе) · файлы/зоны проекта · порядок шагов (конфиг → код → тесты →
README → demo) · критерии готовности · проверки (какие команды/кейсы) · rollback/риск.

### 3.3. Когда нужно перепланирование

Когда стратегия не ложится на задачу: tool вернул ошибку, API недоступен, тесты вскрыли
архитектурную проблему, требований больше, чем ожидалось, или выбранный путь создаёт
лишнюю сложность. Хороший агент **не «долбит стену»**: останавливается, пишет проблему в
state, предлагает новый план, продолжает по нему.

## 4. Tool orchestration

Слой, где агент перестаёт быть чат-ботом и становится рабочей системой: файловая система,
терминал, API, браузер, MCP-серверы, БД, тесты, линтеры. В лекции — обзорно (подробно на
неделе MCP), но базовую механику надо понимать уже сейчас.

### 4.1. Цикл работы с tool

```
1. Tool selection        — выбрать нужный инструмент
2. Tool invocation       — вызвать с корректными аргументами
3. Result interpretation — понять, что вернул
4. Error handling        — обработать ошибку / неожиданный результат
5. State update          — записать, что произошло, перейти к следующему шагу
```

### 4.2. Почему tools сложнее, чем кажется

- Tool может вернуть ошибку API, timeout, неполные данные, неожиданный формат.
- Успешный HTTP-ответ ≠ цель достигнута.
- Агент должен проверять, **тот ли** tool выбрал.
- Результат надо **интерпретировать в контексте плана**, а не вставлять сырым в ответ.
- После каждого вызова — **обновлять state**, иначе агент теряет ход выполнения.

> Пример: «узнать погоду и дать рекомендацию». Плохой агент вызвал weather API и вставил
> сырой JSON. Нормальный — выбрал tool, вызвал с городом/датой, проверил валидность,
> извлёк температуру/осадки/ветер, обновил `state.weather_checked=true`, дал рекомендацию
> с учётом цели.

## 5. Практические принципы работы с агентами

1. **Сужай контекст.** Главный совет лекции: язык, стек, задача, файлы, ограничения,
   формат ответа, критерии готовности. Не заставляй агента плавать в «мировой базе знаний».
2. **Индексируй проект.** Индексация/векторизация помогает находить релевантные файлы;
   критично в больших репозиториях, где ручное добавление файлов забивает окно.
3. **Документируй проект.** Docstrings, README, architecture notes, правила проекта.
   Иногда достаточно дать **сигнатуры функций + комментарии**, а не весь код — экономит
   контекст.
4. **Stage-based execution.** Разбивай работу на стадии и передавай каждую новому/чистому
   контексту — не тащишь мусор предыдущих шагов, меньше галлюцинаций.
5. **Избегай лишней суммаризации.** Summary — «неизбежное зло»: экономит токены, но убивает
   детали. Если можно сохранить **точный state** (список решений, изменённых файлов,
   результат тестов) — сохраняй явно, а не только summary.

## 6. Уровни промптов: simple → pro → pro max

| Уровень | Что это | Проблема / польза |
|---------|---------|-------------------|
| **Simple prompt** | «Напиши функцию проверки простого числа» | не указаны платформа, версия, ограничения, формат, тесты, edge cases → generic-ответ наугад |
| **Pro prompt** | задача + экосистема + стек + протокол + ожидаемые части результата | модель меньше угадывает, работает в нужной области |
| **Prompt pro max / metaprompt** | большой промпт с ролью, стеком, архитектурой, ограничениями, форматом, критериями, процессом | экономит десятки уточняющих сообщений |

Структура metaprompt: `ROLE → PROJECT CONTEXT → TASK → CONSTRAINTS → PROCESS → OUTPUT
FORMAT`.

> Большой промпт **не всегда** «жрёт слишком много контекста». Если он экономит серию
> мутных уточнений и снижает шум assistant-ответов — он выгоднее, чем куча коротких
> запросов.

## 7. JSON и TOON: token-efficient форматы

**TOON** = Token-Oriented Object Notation — компактное представление JSON-like данных для
промптов. Идея: не повторять ключи в каждом объекте массива, а **один раз объявить схему**
и дальше передавать строки значений.

### Почему JSON дорогой для LLM

JSON — стандарт для API, но в prompt многословен: ключи, кавычки, скобки, вложенность
повторяются. На больших массивах = лишние токены, деньги, latency.

```
JSON:
[
  {"id": 1, "name": "Alice", "role": "admin"},
  {"id": 2, "name": "Bob",   "role": "user"}
]

TOON-подобная идея:
users[2]{id,name,role}:
1,Alice,admin
2,Bob,user
```

### Практическое правило

- Для внешних API, строгих контрактов, structured output — **оставайся на JSON / JSON
  Schema**, если этого требует инструмент.
- Для больших однотипных таблиц/массивов *внутрь* prompt — можно пробовать TOON-like.
- Выигрыш зависит от структуры: чем больше однотипных объектов с повторяющимися ключами,
  тем больше экономия.
- TOON — **не универсальная замена JSON**, а prompt-формат для экономии токенов.

## 8. Цель недели (теоретическая рамка)

Познакомиться с context- и memory-management и построить **простой flow работы агента**:
не просто вызвать LLM (как на неделе 1), а сделать маленькую систему, где есть **состояние,
память, планирование и хотя бы один tool**. Минимальный flow:

```
user input → load memory → build context → LLM строит план →
выполнить tool(s) → интерпретировать результат → финальный ответ →
сохранить факты/summary/state
```

Ключ к сдаче — показать **механику**, а не красоту кода: видно, как агент собирает
контекст, использует память, планирует, вызывает инструмент, обновляет state, а при
повторном запуске подгружает сохранённую память.
