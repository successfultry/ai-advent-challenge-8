# Неделя 3 / Лекция 3 — Memory, состояние и stateful-агенты

## Главная мысль

Хороший агент — это **не LLM, которая отвечает на сообщения**, а управляемая система:
`профиль пользователя + состояние задачи + разрешённые переходы + инварианты +
валидация ответа`.

Неделя 2 была про *context management* (что модель видит прямо сейчас). Неделя 3 —
про **memory и state** как часть архитектуры stateful-агента: помощник знает
пользователя, понимает текущую задачу, не перепрыгивает этапы и соблюдает ограничения.

> **Ключевой тезис:** stateful ≠ «LLM магически получила память». State живёт во
> **внешнем слое**: файлы, БД, state storage, profile storage, prompt builder, validation
> logic. Это прямое продолжение тезиса недели 2 (при inference веса не меняются — меняется
> только распределение вероятностей из-за поданного контекста).

Связь с циклом из недели 1 (`perception → memory → reasoning → planning → action →
feedback`): на этой неделе достраиваются **memory** и **planning/feedback** как явные
инженерные компоненты с детерминированными ограничителями вокруг недетерминированной модели.

---

## 1. Контекст недели и главный результат

Третья неделя продолжает вторую: разобрались с context management → теперь memory и state.
Это следующий шаг к собственным агентам, которые можно встроить в код-ассистент,
Telegram-бота, сервис доставки, обучающего помощника, корпоративный ассистент и т.д.

**Что должно получиться к концу недели:**

- агент хранит профиль пользователя и настройки проекта;
- агент понимает текущий этап задачи: `planning / execution / validation / done`;
- агент не нарушает порядок выполнения задачи;
- агент проверяет response по инвариантам;
- агент умеет сохранить состояние и продолжить после паузы;
- архитектура **не привязана к конкретной модели**: OpenAI, DeepSeek, GigaChat и т.д. —
  заменяемые реализации одного `LLMEngine`.

Цель недели — собрать из **персонализации + state machine + инвариантов + prompt builder**
полноценный stateful-agent flow.

## 2. Stateless vs stateful agents

### 2.1. Stateless agent

Отвечает на каждый запрос почти с нуля. Даже если история сообщений сохранена в файле или
в сессии, у него может не быть долговременного профиля, правил приложения, state machine и
инвариантов.

Пример: пользователь просит «Напиши сервис авторизации». Если агент не знает, что проект
всегда на Kotlin/Ktor, он выдаст типовое решение на Python — не потому что Python верный, а
потому что без профиля и ограничений модель идёт по **самой статистически вероятной
траектории**.

Признаки stateless-подхода:

- каждый запрос фактически начинается почти с нуля;
- нет долговременного профиля пользователя или проекта;
- глобальный контекст задачи теряется после новой сессии или summary;
- нет правил/ограничений: стек, город доставки, запрещённые технологии, бюджет;
- агент перепрыгивает этапы — делает то, что попросили прямо сейчас;
- нет долгосрочной стратегии и веса процесса;
- разные пользователи получают примерно одинаковые ответы.

Второй пример (доставка): компания работает только по Москве, но stateless-агент спокойно
пообещает доставку в Иркутск — он не удерживает бизнес-ограничение как постоянное правило.

> **Уточнение:** в сырой транскрибации блок «Особенности Stateful…» по смыслу перечислял
> признаки **stateless**-агента (запрос с нуля, нет истории, забывает контекст). В конспекте
> это исправлено.

### 2.2. Stateful agent

Работает не только с текущим prompt, но и с состоянием: знает этап задачи, профиль,
действующие ограничения и разрешённые переходы.

Пример: state говорит, что задача — «планирование сервиса авторизации», стек — Kotlin+Ktor,
порядок — сначала план, потом код. На «Пропусти план, сразу код» агент **не соглашается
автоматически** — проверяет state machine и требует сначала утвердить план.

Stateful-агент должен: помнить этап задачи · хранить контекст в слоях · знать ограничения ·
контролировать transitions · адаптировать ответ под профиль · сохранять состояние для
продолжения после паузы.

### 2.3. Сравнение

| Критерий | Stateless agent | Stateful agent |
|----------|-----------------|----------------|
| Память | Локальная история или без памяти | Профиль, состояние задачи, summary, сохранённые результаты |
| Процесс | `prompt → response` | `task → state → allowed transition → response → validation` |
| Персонализация | Минимальная или отсутствует | Стиль, constraints, контекст пользователя |
| Ограничения | Легко забываются | Вставляются в prompt **и** проверяются кодом |
| Риск | Галлюцинации, перепрыгивание этапов | Меньше хаоса, но нужна архитектура |

## 3. Персонализация: один request → разные response

Первый строительный блок. Смысл: один и тот же запрос должен давать разные ответы в
зависимости от пользователя, цели, стиля и доменных ограничений.

### 3.1. Три группы данных профиля

| Блок профиля | Что содержит | Пример |
|--------------|--------------|--------|
| **Style** | Формат, тон, глубина ответа | кратко/подробно, формально/разговорно, с кодом/без |
| **Constraints** | Ограничения проекта и пользователя | Python 3.12, FastAPI, без Django, только бесплатные API |
| **Context** | Зачем пользователь пришёл и какой результат нужен | готовится к интервью, делает Telegram-бота, учит язык для поездки |

### 3.2. Интервью при первом запуске

Практичный способ собрать профиль — инициализационное интервью. Telegram-бот видит новый
`user_id`, спрашивает стиль/ограничения/цель, сохраняет профиль в файл или БД.

Примеры вопросов:

1. В каком стиле отвечать: кратко, подробно, с примерами кода?
2. Какой стек по умолчанию?
3. Какие технологии запрещены?
4. Главная цель: учёба, проект, интервью, рабочая автоматизация?
5. Что считать хорошим результатом?

### 3.3. Пример вне программирования

Агент для изучения языка: профиль различает цели — TOEFL/IELTS, разговорная практика,
путешествие, работа, чтение документации. На один запрос «объясни past perfect» ответ для
экзамена и для путешествия должны быть **разными**.

### 3.4. Три слоя памяти

Профиль, состояние задачи и история диалога — это не три отдельных фичи, а **три слоя
одной модели памяти**. Их разделяют по времени жизни и области действия и хранят **отдельно**:

| Слой | Что это | Срок жизни / scope |
|------|---------|-------------------|
| **short-term** | история текущего диалога (`user/assistant`) | одна сессия/чат |
| **working** | контекст задачи: этап, план, решения | одна задача/фича (может жить через несколько сессий); сброс task-scoped |
| **long-term** | профиль: стиль, стек, ограничения, знания | per-user — все чаты/задачи одного пользователя; не стирается при очистке чата |

**Инъекция в запрос:** `long-term + working → system prompt`; `short-term → массив
messages`. Подмешивать только релевантные слои, не сливать всё в один блоб (см. раздел 8,
антипаттерн «всё в одном prompt»).

> **Архитектурный принцип:** system prompt должен пересобираться из актуального состояния
> слоёв на каждый вызов LLM — не кешироваться при инициализации агента. Иначе изменения
> в профиле или состоянии задачи не отразятся на ответах без перезапуска.

> **Терминология:** «working memory» = **task context** из Task State Machine (раздел 5).
> Одно понятие под двумя именами: *working memory* — со стороны модели памяти,
> *task state* — со стороны управляемого процесса.

## 4. Где хранить профиль и как подмешивать его в prompt

Известные инструменты используют похожую архитектуру, но разные места хранения и scope
(слайд «как это делают Claude / Cursor / Claude Code / ChatGPT»). Не копируй один вариант
бездумно — выбирай способ под задачу.

| Инструмент | Где хранится | Scope | Что задаёт | Как инжектится |
|------------|--------------|-------|------------|----------------|
| **Claude** | User Preferences + Project Instructions | глобальный / per-project / per-style | тон, формат, роль, контекст | автоматически в system prompt |
| **Cursor** | `.cursor/rules/*.mdc` файлы | per-project, per-file pattern | стек, архитектура, код-стандарты | через правила проекта + контекст редактора |
| **Claude Code** | `CLAUDE.md` в корне repo | per-repo, наследуется | стек, команды, агенты, правила | prepend к каждому вызову агента |
| **ChatGPT** | Custom Instructions + Memory | глобальный / per-GPT | роль, предпочтения, контекст | автоматически в system prompt |

> **Уточнение (сверено в сети, июнь 2026):** Cursor использует `.cursor/rules/*.mdc` с
> **YAML-frontmatter** и 4 режимами активации (Always / Auto-attached по glob / Agent-requested /
> Manual); старый `.cursorrules` deprecated. Это ровно то, как устроены правила **в нашем
> репозитории** (`.cursor/rules/00-project.mdc` и др.). Подробнее и про кросс-тул стандарт
> `AGENTS.md` — в разделе 12.

> **Подпись на слайде pipeline:** «Неважно, Claude это или Cursor — архитектура одна. Вы
> строите то же самое.» Все инструменты сводятся к одному пайплайну ниже.

### 4.1. Общий pipeline персонализации

`profile storage (.md / DB / API) → profile loader (load(user_id)) → prompt builder
(system + profile + query) → LLM (generate()) → personalized response`

```python
profile = load_profile(user_id)
prompt = build_prompt(query=user_query, profile=profile)
response = llm.generate(prompt)
```

### 4.2. Что класть в system prompt

Если агент работает через HTTP-запрос к LLM, prompt assembly проектируешь сам:

- базовый system prompt: роль агента и режим работы;
- profile: стиль, constraints, контекст;
- summary предыдущей сессии — **если действительно нужно**;
- текущий task state;
- инварианты и запрещённые решения;
- текущий user query.

> **Уточнение:** не клади всё в каждый prompt. Если профиль содержит правила для разных
> режимов (кодинг / язык / документы) — подмешивай только релевантный слой (см. context
> layers, неделя 2). После суммаризации возможен конфликт: решай, добавлять ли профиль
> заново или summary уже содержит стек и вводные.

## 5. Task State Machine

Персонализации мало. Агент должен работать не как свободный чат, а как **управляемый
процесс** — конечный автомат задачи.

### 5.1. Базовые стадии

| State | Смысл (со слайда) | Типичные артефакты |
|-------|-------------------|--------------------|
| `PLANNING` | Собираем требования, утверждаем план | requirements, план, список вопросов |
| `EXECUTION` | Пишем код, создаём артефакты | код, текст, изменения файлов |
| `VALIDATION` | Тесты, ревью, соответствие плану | тесты, code review, сравнение с планом |
| `DONE` | Задача завершена, фиксируем результат | итоговый ответ, сохранённый результат, обновление state |

Цепочка на слайде: `PLANNING → EXECUTION → VALIDATION → DONE`. Стадии можно **расширять**
(planning → отдельно requirements/подход/консилиум; execution → backend/frontend/тесты/ревью;
validation → автотесты/code review/e2e через Playwright), но убирать базовые этапы — крайне
осторожно. Важно не название стадий, а движение задачи через контролируемый процесс.

### 5.2. Allowed transitions

Дают детерминизм недетерминированному агенту. Модель может сгенерировать что угодно, но
приложение не обязано принимать любой переход.

```python
from enum import Enum


class TaskState(str, Enum):
    PLANNING = "planning"
    EXECUTION = "execution"
    VALIDATION = "validation"
    DONE = "done"


ALLOWED_TRANSITIONS: dict[TaskState, set[TaskState]] = {
    TaskState.PLANNING: {TaskState.EXECUTION},
    TaskState.EXECUTION: {TaskState.VALIDATION, TaskState.PLANNING},
    TaskState.VALIDATION: {TaskState.DONE, TaskState.EXECUTION},
    TaskState.DONE: set(),
}


def transition(current: TaskState, target: TaskState) -> TaskState:
    if target not in ALLOWED_TRANSITIONS[current]:
        raise ValueError(f"Transition {current.value} -> {target.value} is forbidden")
    return target
```

> **Слайд «TRANSITIONS» (оригинал на Kotlin):** там тот же автомат через `mapOf(...)` и
> жёсткую проверку `require(target in allowed) { "${ctx.state} → $target запрещён" }`,
> возвращающую `ctx.copy(state = target)`. Суть идентична: переход — это `map +
> require/raise`, а не «как решит модель».

### 5.3. Почему одних промптов мало

Transitions в prompt уже помогают. Но текстовые правила теряются после summary/compacting,
вытесняются новым контекстом или нарушаются моделью (LLM услужлива — согласится пропустить
этап). Для жёстких ограничений transitions хранят и проверяют **в коде**.

> **Ключевая мысль:** prompt — это инструкция, code validation — это ограничитель. Хороший
> агент использует **оба** слоя. Аналогия из лекции: нельзя сначала заселить людей, а потом
> построить дом — порядок процесса задаётся явно.

### 5.4. Injecting state

Слайд «INJECTING STATE»: prompt builder собирает блоки `[STATE] [CURRENT] [PLAN] [DONE]
[PROFILE] [QUERY]` + правила «работай только в рамках current step, не перепрыгивай этапы,
если step завершён — верни next_step».

```python
def build_prompt(query: str, task: dict, profile: dict) -> str:
    return f"""
[STATE]
{task['state']} step {task['step']}/{task['total_steps']}
[CURRENT]
{task['current']}
[PLAN]
{task['plan']}
[DONE]
{task.get('done', '')}
[PROFILE]
{profile}
[QUERY]
{query}

Rules:
- Work only inside the current step.
- Do not jump to future stages.
- If the step is complete, return next_step.
""".strip()
```

### 5.5. Более жёсткая изоляция стадий

Если нужно усилить контроль — разделять стадии не только промптами: разные функции, разные
LLM-сессии, разные процессы/Docker-контейнеры, отдельные изолированные агенты. Каждой стадии
отдавать **только её задачу**, а не весь план. Код детерминированнее текстовой инструкции.

## 6. Сохранение и возобновление задачи

Stateful-агент продолжает работу после паузы (пропал интернет, закрыли ПК, кончились токены,
прошло 12 часов): загрузил state → продолжил с нужного места.

**Что сохранять:** `task_id` и `user_id` · текущий state · утверждённый план · результаты
каждого этапа · profile · constraints и invariants · последний user query и важные решения ·
allowed transitions / версия state machine.

```json
{
  "task_id": "auth-service-001",
  "user_id": "victor",
  "state": "execution",
  "plan": ["define API", "implement JWT", "add tests"],
  "current": "implement JWT token validation",
  "done": ["requirements collected", "plan approved"],
  "profile_ref": "profiles/victor.yaml",
  "invariants_ref": "projects/ai_advent/invariants.yaml"
}
```

> **Уточнение:** не храни только summary. Summary компактно, но теряет детали. Структурный
> state (stage, plan, constraints, results) храни **отдельно** — это перекликается с тезисом
> недели 2 «избегай лишней суммаризации, сохраняй точный state».

## 7. Инварианты и валидация ответа

Инварианты — ограничения, которые **не меняются от запроса к запросу**. В лекции они часто
описаны как «то, что запрещено», но технически инвариант — это и запрет, **и** обязательное
требование.

### 7.1. Примеры инвариантов

| Тип | Примеры |
|-----|---------|
| Стек | Python 3.12, FastAPI, PostgreSQL, Redis; или Kotlin, Ktor, Compose |
| Архитектура | MVI, ViewModel для состояния, слои domain/application/infrastructure |
| Запреты | не использовать RxJava, AsyncTask, Java, платные API |
| Доменные | доставка только по Москве; только японский язык; только бесплатные модели |
| Процесс | сначала plan, потом execution, потом validation |

Инварианты полезны даже когда финальная архитектура неизвестна: можно не знать, *как* надо,
но точно знать, *чего нельзя*.

### 7.2. Injecting invariants

Слайд «INJECTING INVARIANTS» — pipeline: `Invariants → Prompt Builder → LLM → Validate →
Pass/Fail`. Сначала инварианты вставляются в prompt («Нарушение любого инварианта
ЗАПРЕЩЕНО»), затем response проверяется **отдельно** кодом.

```python
class Invariant:
    def __init__(self, name: str, description: str, forbidden_patterns: list[str]) -> None:
        self.name = name
        self.description = description
        self.forbidden_patterns = forbidden_patterns

    def check(self, response: str) -> list[str]:
        violations = []
        lower = response.lower()
        for pattern in self.forbidden_patterns:
            if pattern.lower() in lower:
                violations.append(f"Invariant '{self.name}' violated: found '{pattern}'")
        return violations


def validate_response(response: str, invariants: list[Invariant]) -> list[str]:
    errors = []
    for invariant in invariants:
        errors.extend(invariant.check(response))
    return errors
```

> **Уточнение:** подстрочный `pattern in lower` — простейший демо-чек. Он ловит запрет
> «RxJava», но даст и ложные срабатывания (упоминание в отрицании: «не используй RxJava»).
> Для серьёзной проверки — регулярки/AST/линтер либо LLM-судья (см. неделя 1, LLM-as-judge).
> Обязательные инварианты («ответ в JSON», «использован FastAPI») проверяются не запретами,
> а позитивной валидацией (наличие/парсинг).

### 7.3. Retry loop

```python
MAX_RETRIES = 3

query = read_user_query()
for attempt in range(MAX_RETRIES):
    prompt = build_prompt(query=query, profile=profile, state=state, invariants=invariants)
    response = llm.generate(prompt)
    violations = validate_response(response, invariants)
    if not violations:
        send(response)
        state = next_state(state, response)
        save_state(state)
        break
    # feedback модели: что нарушено — на следующей итерации
    query = "Исправь ответ. Нарушения: " + "; ".join(violations)
else:
    send_warning("Не удалось получить ответ без нарушений инвариантов")
```

> **Уточнение / корректировка:** на слайде (и в источнике) retry был `while (true)` без
> лимита — это риск бесконечного цикла и сжигания токенов. Добавлен `MAX_RETRIES` и ветка
> `else` с warning'ом. Это согласуется с правилом репозитория «aux-вызовы best-effort, не
> ломать основной поток».

> **Ключевая мысль:** инварианты — это **линтер для требований, выраженных человеческим
> языком**, а не только синтаксисом кода.

## 8. Антипаттерны

| Антипаттерн | Почему плохо | Как исправить |
|-------------|--------------|---------------|
| Всё в одном prompt (`profile + state + history + invariants + query`, ~50k токенов) | Контекст переполняется, модель теряет фокус, ответ деградирует | Делить на слои, инжектить только нужное для текущего шага |
| Нет validation transitions | LLM услужлива по природе — без `require()` согласится на любой переход | Переходы — в коде: `map + require()`; LLM не решает, код решает |
| Инварианты только в тексте | Текстовые правила = просьба, не закон; LLM может нарушить, нет гарантий | Двойная защита: prompt + код-валидация (`check()`) после генерации |
| Summary вместо state | Summary теряет детали и искажает смысл | Хранить структурный state отдельно |
| Один профиль на всё | Профиль для кодинга мешает профилю для языка | Scope профиля: global / per-project / per-task / per-mode |

## 9. Архитектура stateful-агента

Слайд: `User Query + Profile (style, constraints) + State Machine (этап, шаг, план) +
Invariants (stack, arch, rules) → Prompt Builder → LLM → Validate → Pass/Fail`.
Pass → response пользователю + State Update. Fail → retry с описанием нарушений.

### 9.1. Компоненты

| Компонент | Ответственность |
|-----------|-----------------|
| `ProfileStorage` | Хранит/загружает профиль: style, constraints, context |
| `TaskStateStorage` | Хранит состояние задачи, план, текущий этап, результаты |
| `StateMachine` | Проверяет разрешённые transitions |
| `InvariantChecker` | Проверяет response по правилам и запретам |
| `PromptBuilder` | Собирает system/user prompt из релевантных блоков |
| `LLMEngine` | Абстракция над провайдером: OpenAI, DeepSeek, GigaChat, локальная LLM |
| `ResponseValidator` | Объединяет invariant check, формат ответа, проверку state output |

### 9.2. Почему важны интерфейсы

Не привязывай агента к конкретному OpenAI/DeepSeek-клиенту. Определи интерфейс `LLMEngine` и
инжектируй провайдера — тогда модель меняется без переписывания prompt builder, state machine
и validation. Поддерживаемость через интерфейсы + SOLID; агент может быть из нескольких файлов.

```python
from typing import Protocol


class LLMEngine(Protocol):
    def generate(self, prompt: str) -> str: ...


class PromptBuilder(Protocol):
    def build(self, query: str, profile: dict, state: dict, invariants: list[dict]) -> str: ...


class Agent:
    def __init__(self, llm: LLMEngine, prompt_builder: PromptBuilder) -> None:
        self.llm = llm
        self.prompt_builder = prompt_builder
```

> **Ключевая мысль:** даже 2–3 хорошо спроектированных файла (state machine + prompt builder +
> invariant checker) резко улучшают агента/код-ассистента. Вопрос не в размере кода, а в
> качестве архитектурной сборки.

## 10. Цель недели (практическая рамка)

Итог недели — собрать из строительных блоков **stateful-агента**. Дни, вероятно, пойдут по
нарастающей: персонализация → task state machine → инварианты → объединение в общий pipeline.
Минимальный flow, который надо показать:

```
user_id + query → load_profile → build_prompt (profile + state + invariants) →
LLM → validate (invariants + allowed transition) →
pass: send + update/save state | fail: retry с описанием нарушений
```

**Минимум, который стоит реализовать:**

- профиль пользователя (style / constraints / context), при первом запуске — короткое интервью;
- task со state `PLANNING / EXECUTION / VALIDATION / DONE`, allowed transitions **в коде**;
- инварианты в prompt **и** отдельная проверка response кодом + retry при нарушении;
- сохранение state на диск и продолжение после перезапуска;
- LLM спрятана за интерфейсом (`LLMEngine`), провайдер заменяем.

**Демо-сценарий для видео:**

1. Показать профиль (стиль, стек, ограничения).
2. Создать задачу «сервис авторизации» → агент входит в `PLANNING` и **не пишет код сразу**.
3. «Пропусти план, сразу код» → агент отказывает / просит утвердить план (запрет transition).
4. Утвердить план → переход в `EXECUTION`.
5. Смоделировать response с запрещённой технологией (RxJava/Java/Django) → invariant checker
   ловит нарушение и просит переделать.
6. Перезапустить приложение → task state восстановился.

> Ключ к сдаче — показать **механику** stateful-агента (профиль, state, переходы, инварианты,
> сохранение/восстановление), а не красоту кода.

## 11. Корректировки и технические уточнения (из источника)

Технические уточнения:

- LLM сама по себе не становится stateful — поведение создаёт внешний слой.
- System prompt важен, но не абсолютен; критичный запрет проверяй кодом.
- Инвариант — не только запрет, но и обязательное свойство («использовать FastAPI», «ответ
  в JSON», «сначала план»).
- State machine не гарантирует истинность ответа модели — гарантирует **порядок процесса**.
- Summary ≠ полноценный state storage.
- Персонализация должна быть scoped: global / per-project / per-task / per-mode.
- Слайды презентации — на Kotlin (Android-аудитория); код здесь дан на Python, смысл идентичен.

## 11.5. Pipeline of stage-agents (Day 13 — расширение FSM)

Лекция описывает FSM на уровне данных (allowed transitions map + validate). Следующий шаг —
перевести FSM из «мета-уровня» (этап записан в контексте задачи) в **операционный уровень**:
каждая стадия становится отдельным агентом со своим изолированным контекстом.

### Детерминированные vs. LLM-driven transitions

| Подход | Как выбирается следующая стадия | Детерминизм |
|--------|---------------------------------|-------------|
| LLM-driven | Модель сама называет следующую стадию в ответе | Нет — галлюцинации + prompt injection |
| Deterministic | Переход вычисляет код по артефакту стадии | Да — независимо от содержания ответа |

**Правило**: LLM принимает содержательные решения внутри стадии (что написать в плане, как
реализовать, что проверить), код принимает структурные решения (куда двигаться дальше). Даже
ветвление (валидация прошла/провалилась) делает код: он читает поле статуса из артефакта, а не
позволяет модели назвать целевую стадию.

### Связь с 6-стадийным циклом агента

Цикл `perception → memory → reasoning → planning → action → feedback` из недели 1 работает
**внутри** каждого стадийного агента при каждом LLM-вызове. 4 стадии задачи (planning /
execution / validation / done) — это уровень выше: как задача движется через систему, а не как
один вызов проходит через нейросеть.

```
Система: planning ──► execution ──► validation ──► done
                                                     ↕ (детерминированно, код)
Каждый LLM-вызов: perception → memory → reasoning → planning → action → feedback
```

### Pause/Resume и lossless state

Stateful-агент из раздела 6 продолжает работу после паузы. Ключевое требование к pipeline:
артефакты каждой стадии должны быть **сохранены до того, как задаётся вопрос пользователю**.
Тогда возобновление после перезапуска = загрузить состояние задачи с диска → вычислить текущую
стадию → передать артефакты в system prompt → продолжить. Никаких «объясни мне снова».

### Artifact contract и forward-only передача

Чтобы не загрязнять контекст следующей стадии историей предыдущей, артефакты передаются
только через **system prompt** (а не через общую историю сообщений). Каждый стадийный агент
видит: `профиль + контекст задачи + прошлые артефакты (в system) + только свои user/assistant
пары`.

### 12.2. Cursor rules — текущий формат

`.cursor/rules/*.mdc` = YAML-frontmatter (`description`, `globs`, `alwaysApply`) + markdown.
4 режима активации: **Always Apply** · **Apply Intelligently** (агент решает по `description`) ·
**Apply to Specific Files** (по `globs`) · **Manual** (`@rule-name`). `.cursorrules` deprecated
и игнорируется в Agent mode. Это **тот самый механизм**, на котором держатся правила нашего
репозитория (`.cursor/rules/00-project.mdc`, `10-python.mdc`, `20-agent-architecture.mdc`).

### 12.3. LangGraph — реальный фреймворк stateful-агентов

Прод-стандарт «task state machine для LLM» (v1.0 в конце 2025, v1.2.5 от 2026-06-12; Klarna,
Uber, LinkedIn, Replit, J.P. Morgan). Моделирует агента как граф: **State** (typed `TypedDict`/
Pydantic) + **Nodes** (функции) + **Edges** (переходы, в т.ч. условные и циклы для
retry/reflection). Ключевое для недели 3 — **checkpointer** (Postgres/SQLite/in-memory) для
durable execution: агент падает/паузится и **возобновляется с того же места по `thread_id`** —
это ровно раздел 6 «сохранение и возобновление». LangChain в отчёте 2026 приписывает **>60%
прод-инцидентов агентов** именно проблемам со state management — что подтверждает тезис лекции,
почему state нужно проектировать явно.

> Для задания фреймворк брать не обязательно (правило репо: ask before heavy deps, строим
> минимально). Но `TaskState` + `ALLOWED_TRANSITIONS` + checkpoint-файл из лекции — это
> *ручная мини-версия* того же, что LangGraph даёт из коробки. Полезно как ориентир
> терминологии (State / Node / Edge / checkpointer) и как honest comparison в видео.
