# Неделя 5 / Лекция 5 — RAG: Retrieval-Augmented Generation

> Конспект лекции 5. Сведён из транскрибации (`Nueva grabacion 2 1m4a.txt`), двух
> расширенных PDF-конспектов (GPT) и скринов презентации (flowchart, pipeline, VECTOR,
> PROBLEM, RERANKING, метрики, LIMITS OF RAG). Где формулировки лектора были
> грубыми/устаревшими — взята технически корректная версия (отмечено как **Уточнение**).
> GPT-конспекты проверены, практическая часть из них намеренно выброшена. Это теория, не
> скелет задания (формулировки заданий — в [`challenge-tasks.md`](./challenge-tasks.md)).

## Главная мысль

Неделя 5 продолжает цепочку предыдущих: после context/memory (неделя 2–3) и MCP/tools
(неделя 4) фокус смещается на **vector retrieval** как способ доставать релевантные знания из
большой базы во время inference. RAG — это не магия и не замена fine-tuning; это инженерный
способ подмешивать нужные chunks в prompt, когда общая модель не знает твои внутренние
документы.

> **Ключевой тезис:** RAG **не меняет веса модели**. Если в следующий запрос не подмешать
> документы заново — модель снова отвечает только из общего обучения и текущего prompt.

Связь с циклом из недели 1 (`perception → memory → reasoning → planning → action →
feedback`): RAG — это реализация стадии **memory** (конкретно vector retrieval, который в
неделе 2 был лишь одной строкой в таблице техник). Найденные chunks — это **perception**
(внешние факты как вход), а citations/feedback замыкают **feedback**.

## 1. Что такое RAG и чем отличается от MCP

**RAG = Retrieval-Augmented Generation** — паттерн дополнения ответа LLM внешними знаниями
во время inference. Не одна модель и не библиотека, а **архитектурный паттерн**: сначала
*достать* (retrieval) релевантные знания, потом *дополнить* (augment) ими prompt, потом
*сгенерировать* (generate) ответ с опорой на них.

| Шаг | Что происходит | Зачем |
|-----|----------------|-------|
| **Retrieval** | Поиск релевантных chunks в базе знаний / vector store | найти факты, на которые модель должна опереться |
| **Augmentation** | Найденные chunks вставляются в prompt вместе с вопросом | дать внешний контекст прямо во время inference |
| **Generation** | LLM формирует ответ, желательно со ссылками на источники | связный, проверяемый результат |

### 1.1. RAG vs MCP — где граница

Лектор формулирует так: **MCP — про общение с внешними источниками/данными и действиями,
RAG — про общение с внутренними знаниями**. На вход RAG идут *знания* (документы, регламенты,
история), а не просто «данные из стороннего API».

> **Уточнение:** дихотомия «внешнее (MCP) vs внутреннее (RAG)» — упрощение. Точнее: **MCP —
> это tools/actions/протокол доступа** (сходить в календарь, дёрнуть API, создать тикет), а
> **RAG — это retrieval знаний** (найти релевантные фрагменты и положить в контекст). RAG
> тоже может искать по внешним документам, а MCP-сервер может отдавать knowledge-resources.
> Разница не во «внутри/снаружи», а в *retrieval знаний* vs *вызов инструментов*.

На практике **комбинируются**: MCP-tool достаёт документ из Confluence → RAG-компонент
индексирует, ищет и ранжирует его chunks.

## 2. Зачем RAG: проблемы общей модели

Базовая LLM обучена на огромном **публичном** корпусе (веб, книги, GitHub, Reddit, форумы) —
и не знает твой Confluence, Jira, Notion, локальные регламенты, договорённости команды,
актуальные версии документов, семейный/личный архив. Лектор выделяет три беды «сырого»
контекста:

1. **Контекст не полный** — модель не видела твои внутренние данные.
2. **Контекст смешанный** — дубликаты, разные годы, противоречивые версии одного процесса
   (у каждой команды свой perf-review, в каждом году новые правила). Нейронка **не человек**
   и не отделит «правильную» статью от устаревшей — возьмёт свежую или статистически
   вероятную, но это не факт, что верную.
3. **Контекст большой** — даже сложенный в Markdown, он не влезет в окно, а поиск по сырому
   MD плохой. Перелопатить весь Confluence — медленно и дорого.

### 2.1. Ложноположительный ответ опаснее явной ошибки

Главный риск — **не неправильный ответ, а похожий на правильный**. Ложноотрицательный
(«данные явно кривые») не страшен: человек видит и идёт искать дальше. А правдоподобная
галлюцинация, принятая некомпетентным или спешащим человеком за факт, — вот это опасно
(«нейронка сказала» = просто отражение твоего же запроса).

> Поэтому хороший RAG обязан **помогать проверять**: показывать источники, даты, названия
> документов, фрагменты и, если можно, score/confidence — а не «просто что-то найти».

### 2.2. Пример из лекции: code review policy

| Без RAG | С RAG |
|---------|-------|
| «Обычно code review требует 1 approval, ревью в течение недели» — среднее по интернету, нет источника, галлюцинация | «В нашем проекте: минимум 2 approval до merge, review ≤ 24 часов» + ссылка на внутренний `code_review_policy` в Confluence/GitHub |

## 3. Способы «тюнить» LLM: context optimization vs LLM optimization

Лектор делит улучшение модели на две оси (см. скрин flowchart `Prompt engineering → Evaluate
and identify the gaps → RAG / Fine-tuning`):

- **Context optimization** — *что* модель должна знать. Сюда входят **prompt** (в широком
  смысле: skills, субагенты, MD-файлы) и **RAG**.
- **LLM optimization** — *как* модель должна действовать. Это **fine-tuning**: меняем веса,
  перераспределяем важность связей между уже имеющимися знаниями.

| Подход | Что оптимизирует | Когда брать | Что НЕ решает |
|--------|------------------|-------------|---------------|
| **Prompt engineering** | инструкции, формат, роль, стиль, ограничения | быстро управлять поведением без внешней базы | нет надёжного доступа к большому корпусу знаний |
| **RAG** | контекст: какие факты модель получает на inference | ответы по документам/wiki/policy/договорам | не меняет навык/стиль, не заменяет бизнес-логику |
| **Fine-tuning** | веса: склонность модели отвечать/действовать | устойчивый стиль, формат, доменная манера, классификация | плохой способ хранить **часто меняющиеся** факты |

> **Главное (со скрина):** это **аддитивные, а не эксклюзивные** вещи (`additive, not
> exclusive`). Промышленное «обучение» ChatGPT и аналогов = prompt engineering + RAG +
> fine-tuning **вместе**. Для конкретного кейса используют и RAG, и fine-tuning сразу.
>
> RAG лучше для **часто меняющихся фактов** (policies, цены, процессы, актуальная
> документация); fine-tuning — для **устойчивого поведения/стиля/формата**.

> **Уточнение (правка транскрибации):** лектор говорит, будто fine-tuning можно «провести
> после ответа как реакцию на пробел». Технически fine-tuning — **отдельный процесс
> обучения/адаптации**, а не быстрый шаг внутри одного ответа. В runtime «реакция на пробел»
> делается через retrieval, feedback, обновление prompt/memory и evals — не дообучением.

## 4. Где применяется RAG

- **Корпоративные базы знаний** — Confluence, Notion, wiki, регламенты, policies, FAQ.
- **Чаты и переписки** — Slack/Telegram/Teams/Discord (если есть право и смысл индексировать).
- **Privacy / закрытый контур** — RAG часто крутят на **локальной** модели: данные не
  покидают контур. Возможен «консилиум»: глобальная модель даёт общий ответ → локальная
  модель с RAG-знаниями дотюнивает его в закрытом контуре.
- **Специализированные агенты** — медицина, лабораторная диагностика, физика, механика,
  юриспруденция, образование: всё, где нужны узкие доменные знания.
- **Глобальный анализ трендов** — векторизованный массив документов → длинное исследование.
- **Цифровой двойник** — персональная история (переписки, звонки, видео, заметки),
  оцифрованная и сложенная в личную базу.

## 5. Pipeline RAG

Базовая схема из презентации (`User → Chat Completion → Retrieval → Combine content with
prompt → Answer`). Заметь: все API называются *completions* — completion «изучает» вопрос,
лезет в документы, комбинирует найденное с promptом, возвращает результат. Отчасти похоже на
MCP, но суть другая (поиск знаний, а не вызов tool).

Полный инженерный pipeline (важно: сломаешь одну стадию — ответ деградирует даже на сильной
модели):

```
1. Ingest        — собрать данные (PDF, MD, HTML, Confluence, Notion, GitHub, Jira, чаты)
2. Clean/normalize — убрать мусор: футеры, навигацию, номера страниц, битую разметку, OCR-шум
3. Chunking      — порезать документы на осмысленные фрагменты (+ overlap)
4. Embeddings    — chunks и запрос пользователя → векторы
5. Vector store  — сохранить векторы + metadata
6. Retrieval     — найти top-k похожих chunks по query-вектору
7. Reranking     — переупорядочить найденное более точной моделью (опционально)
8. Prompt build  — вопрос + найденные chunks + правила ответа
9. Generation    — ответ от LLM
10. Citations    — показать источники/фрагменты, на которых основан ответ
11. Evaluation   — измерить качество, собрать feedback, улучшать pipeline
```

### 5.1. Что хранить вместе с chunk (metadata)

| Metadata | Зачем |
|----------|-------|
| `document_id` | понимать, из какого документа пришёл chunk |
| `title` | показывать нормальный источник, а не UUID |
| `url` / `path` | дать ссылку на исходник |
| `created_at` / `updated_at` / `status` | фильтровать устаревшее, ловить deprecated/archived |
| `section heading` | место chunk внутри документа |
| `access level` | не показывать то, к чему у юзера нет прав |
| `chunk_index` | восстанавливать соседние chunks и порядок |

> Metadata — это не украшение. Без `updated_at`/`status` нельзя отличить актуальную policy от
> прошлогодней; без `access level` юзер получит chunk из чужого проекта.

## 6. Embeddings: текст → вектор

**Generative model** и **embedding model** — разные роли. Это ядро понимания RAG.

| Модель | Вход | Выход | Зачем |
|--------|------|-------|-------|
| **Generative** | prompt / контекст / сообщения | текст, код, JSON, reasoning | сформулировать ответ |
| **Embedding** | текстовый фрагмент | вектор чисел | semantic search, retrieval, clustering, dedup |
| **Reranker / cross-encoder** | query + кандидат вместе | оценка релевантности пары | точный отбор лучших chunks |

### 6.1. Семантика через векторы и cosine similarity

Вектор — это «много цифр», кодирующих **смысл** текста. Близость по смыслу = близость
векторов, измеряется **косинусным сходством** (cosine similarity):

- `cos ≈ 1` — тексты близки по смыслу («SpaceX основан в 2002» ↔ «SpaceX основан Маском в 2002»);
- `cos ≈ 0` — тексты о разном, не пересекаются (параллельные, не противоположные);
- `cos ≈ -1` — противоположны по направлению вектора.

> **Уточнение:** в реальных embedding-моделях «семантическая противоположность» **не всегда
> буквально -1**. cosine similarity — математическая метрика по направлению векторов, а не
> человеческая логика «антонимов». На практике у нормальных текстов значения чаще лежат в
> положительной зоне, а не растянуты на весь `[-1; 1]`.

### 6.2. Размерность вектора (dimension)

Одно слово/предложение превращается в большой вектор: типичные размерности — **768, 1024,
1536, 3072**. Чем больше измерений, тем тоньше различия (аналогия лектора: близость по осям
x/y/z, только осей не 3, а 768). Аналогия с хэш-функцией: слабая → много коллизий, сильная →
коллизий почти нет; много измерений = меньше «семантических коллизий» между разными словами.

> **Уточнение (важная правка транскрибации):** числа 768/1024/3072 — это **dimension
> embedding-вектора**, а **не «количество параметров модели»**. Это разные вещи. Размерность
> влияет на точность/скорость/стоимость поиска; параметров у самой модели — отдельная история.

### 6.3. Как embedding-модель «понимает» смысл (обучение)

Со скрина `VECTOR`, общий процесс для предложения:

```
Input text: "SpaceX was founded in 2002"
  → tokenization      → ["Space","X"," was"," founded"," in"," 2002"]
  → embedding layer    → каждому токену свой вектор: "Space" → [0.2, 0.8, -0.4, ...]
  → transformer/attention → self-attention уточняет вектор каждого слова с учётом соседей
  → pooling            → усреднение векторов токенов → один вектор всего предложения
  → similarity search  → сравнение с сохранёнными векторами
```

- **Attention** перестраивает вектор каждого слова с учётом контекста предложения (вектор
  взаимосвязанности, не только отдельного слова).
- **Pooling** (усреднение/нормализация) сводит векторы токенов к **одному вектору
  предложения** — потому что искать надо по смыслу предложения, а не отдельных слов.
- На практике мы работаем с **готовыми** моделями — нужен лишь механизм сравнения вектора
  запроса с сохранёнными векторами.

## 7. Chunking: как резать базу знаний

Chunking — одна из самых важных частей RAG. Плохой chunking убьёт ответ даже при сильной
модели и хорошем vector store. Идея: режем документ на фрагменты → векторизуем → кладём в
store; на запрос ищем близкие chunks.

| Тип | Как работает | Плюсы | Минусы |
|-----|--------------|-------|--------|
| **Fixed-size** | режем по N токенов/символов (напр. каждые 500) | просто, удобно для MVP | рвёт предложение/смысл на границе |
| **Fixed-size + overlap** | каждый chunk частично перекрывает предыдущий | смысл не теряется на границе | больше chunks → дороже хранить/искать |
| **Semantic** | режем по заголовкам, абзацам, смысловым блокам | лучше сохраняет смысл | сложнее реализовать/тестировать |
| **Metadata-aware** | учитываем title, section, тип, дату, автора | лучше фильтрация и объяснимость | надо вести и чистить metadata |

### 7.1. Overlap

Без overlap фраза может разорваться: «when a user» попало в один chunk, «ask a question» — в
другой, и retrieval найдёт лишь половину смысла. Перекрытие закрывает границу: вместо
`[0–500], [500–1000]` берём `[0–500], [450–950], [900–1400]` — куски пересекаются.

Типовой ориентир: **chunk 500–1000 токенов, overlap 50–200 токенов (≈10–20%)**.
Универсального числа **нет** — размер chunk и overlap подбирают **экспериментально** под свои
документы, модель и задачу. В ИИ «без эксперимента не обойтись».

### 7.2. Что ломает chunking

- PDF с колонками/футерами/номерами страниц, попадающими в каждый chunk.
- Сканы без нормального OCR.
- Таблицы, где строки теряют заголовки колонок.
- Markdown без заголовков / с кривой структурой.
- Дубликаты документов за разные годы.
- Слишком короткие chunks (нет смысла) или слишком длинные (несколько тем сразу).

## 8. Tooling: Ollama и локальные embedding-модели

Лектор хвалит **Ollama** (в транскрибации «Allama/АЛАМА») для embeddings: локально (данные не
покидают комп), ~нулевая цена, скорость тут не критична (векторизуешь не на каждый чат),
параметров немного, совместимо с облачными эмбедерами, удобно тестировать RAG на малых
размерах.

> **Уточнение (правка транскрибации):** Ollama — **не «лучшая модель»** и вообще **не модель**.
> Это локальный **runtime / model server**, через который запускают *разные* модели, включая
> embedding-модели. «Лучшесть» зависит от конкретно выбранной модели, данных и железа.

> **Уточнение:** «если RAG хорошо работает на маленькой модели — на большой будет прекрасно»
> — **не гарантировано**. Качество retrieval зависит от embedding-модели, chunking, metadata,
> reranking, данных и prompt builder, а не только от размера модели.

### 8.1. Нормализация векторов

Лектор: «нормализация = поделить все числа вектора на максимальное» (получить `[0; 1]`).

> **Уточнение:** для embedding-search обычно нужна **L2-нормализация** — приведение вектора к
> **единичной длине** (делим на евклидову норму), чтобы cosine similarity корректно сравнивала
> *направления*. Деление на максимум — это про min-max масштабирование, оно **не** даёт
> корректную норму для косинуса. Многие embedding-библиотеки уже возвращают нормализованные
> векторы или умеют нормализовать сами.

## 9. Retrieval и reranking

### 9.1. Retrieval: top-k и фильтры

На retrieval вопрос пользователя тоже превращается в embedding, vector store ищет chunks с
максимальной близостью к query-вектору. Достаётся **top-k** (top-5/10/20/50):

- **k маленький** → можно не достать нужный документ;
- **k большой** → prompt забивается шумом, растёт стоимость, модель «смешивает темы»;
- **metadata-фильтры** (дата, проект, команда, тип, права доступа) сужают поиск.

### 9.2. Проблема: похоже ≠ релевантно (скрин `PROBLEM`)

Запрос «Как настроить CI/CD для Kotlin Multiplatform?» по вектору одинаково «похож» на:
- ✅ «Настройка GitHub Actions для KMP» — релевантно;
- ✗ «Обзор CI/CD инструментов 2023» — похоже по вектору (есть «CI/CD»), но **не отвечает** на
  вопрос.

Если просто отдать LLM top-20 — быстро, но неточно.

### 9.3. Reranking: bi-encoder vs cross-encoder (скрин `RERANKING`)

Решение — второй, более точный отбор отдельной **cross-encoder** моделью.

| | **Bi-encoder** (retrieval) | **Cross-encoder** (reranking) |
|---|---|---|
| Как работает | query и chunk кодируются **отдельно** в embeddings, потом сравниваются | смотрит query + chunk **вместе**, оценивает релевантность пары |
| Скорость | быстро (миллисекунды) | медленно (миллисекунды–секунды) |
| Точность | средняя — годится для первичного отсева | высокая — точный отбор |
| Когда | первый этап (top-20) | второй этап (top-20 → top-5) |

Pipeline: `query → bi-encoder: top-20 → cross-encoder rerank: top-5 → LLM → answer + citations`.

> Reranking **не делает ответ автоматически истинным**, но резко повышает шанс, что в prompt
> попадёт релевантный контекст, но не гарантирует правильность ответа. Применяется только к
> уже отобранным top-k, так как стоит замедлением.

## 10. Метрики качества RAG (скрин с тремя метриками)

RAG нельзя оценивать «на глаз» — иначе получишь красивое демо, которое разваливается на
реальных документах. Три базовые метрики:

| Метрика | Вопрос | Низкое значение = |
|---------|--------|-------------------|
| **Context relevance** | нашли ли мы правильные chunks? | плохой retrieval (достаём нерелевантное/устаревшее) |
| **Faithfulness** | ответ основан на найденном контексте? | модель галлюцинирует / добавляет утверждения не из chunks |
| **Answer correctness** | финальный ответ правильный? | даже при хороших chunks модель неверно синтезировала ответ |

Как мерить на практике:
- **Ручной feedback** — палец вверх/вниз (как в ChatGPT) на «правильные ли чанки» и «есть ли
  ссылки/основан ли на контексте». Собираешь стату → видишь, где плохо, можно сузить область.
- **Эталонный набор (golden dataset)** — заранее заданные вопросы + правильные ответы +
  допустимые источники. Можно гонять автоматически (в т.ч. другой моделью) и сравнивать.
- **Логирование (prod)** — query, найденные chunks, final answer, источники, оценки, ошибки.

> Если retrieval регулярно возвращает нерелевантные chunks, это сигнал к пересмотру chunking,
> embedding-модели или метаданных. Если ответ часто «из головы», а не из chunks — возможно,
> RAG подмешивается реже, чем нужно.

## 11. Когда RAG не поможет (скрин `LIMITS OF RAG`)

RAG **не универсальная таблетка**. Он закрывает доступ к знаниям, но не всё поведение агента.

| RAG не поможет | Почему | Что вместо/дополнительно |
|----------------|--------|--------------------------|
| **Мало / плохие данные** | нечего искать, документы шумные, плохо размечены | data cleaning, OCR, разметка, нормализация, сбор базы; иногда **fine-tuning** |
| **Нужна сложная логика** | RAG достаёт факты, но не заменяет workflow | **prompt engineering**, agents + tools, state machine, business rules |
| **Нужен устойчивый стиль/тон/формат** | RAG хранит сырые размеченные **факты**, а не манеру | personalization (неделя 3), prompt engineering, fine-tuning |
| **Устаревший формат** (сканы, амбарные книги, таблицы, рукописное) | текст недоступен/плохо извлекается | OCR, structured extraction, **multimodal RAG**, ручная оцифровка |
| **Действия во внешнем мире** | RAG не создаёт встречи и не меняет таски | **MCP/tools/API** (неделя 4) |

## 12. Антипаттерны и риски RAG

| Антипаттерн | Почему плохо | Как исправить |
|-------------|--------------|---------------|
| Индексировать всё подряд без очистки/metadata | шум в store, плохой retrieval | clean-up, dedup, metadata на ingestion |
| Игнорировать даты/версии документов | ответ по устаревшей policy | `updated_at`/`status`, фильтры, deprecated/archived |
| Не показывать sources | ответ сложно проверить | рекомендуется выводить title + path/url + chunk_id |
| Класть в prompt слишком много chunks | ответ превращается в шум, темы смешиваются | reranking + брать top-n после rerank |
| Доверять только vector similarity | «похоже» ≠ «релевантно» | reranking + metadata-фильтры (+ hybrid, §13) |
| Не проверять права доступа | юзер получит chunk из чужого проекта | `access level` в metadata, фильтрация |
| Нет fallback при пустом retrieval | модель начинает выдумывать | при score ниже порога — честно «данных не найдено» |
| Считать, что RAG заменяет fine-tuning/agents/logic | разные задачи | комбинировать, не подменять |
| Не защищаться от prompt injection **внутри документа** | документ может содержать вредную инструкцию для LLM | sanitize контента, не исполнять инструкции из chunks, изоляция |

> Связь с неделей 4: prompt injection внутри индексируемого документа — та же поверхность
> атаки, что и в tools. Опасное должно ловиться **кодом/валидацией**, а не «просьбой в промпте».

## 13. Корректировки и технические уточнения (сводка)

| Фрагмент из транскрибации | Корректная формулировка |
|---------------------------|-------------------------|
| «RUG / RAC / рак» | Ошибка распознавания. Правильно: **RAG — Retrieval-Augmented Generation** |
| «RAG подгружает знания в базу/мозг модели» | Веса **не меняются**. RAG подмешивает найденные chunks в **prompt** на время конкретного inference |
| «Ollama — лучшая модель» | Ollama — **runtime/model server** для локального запуска моделей, не модель. Качество зависит от выбранной модели |
| «768/1024/3072 — параметры модели» | Это **dimension embedding-вектора**, а не число параметров модели |
| «нормализация = деление на максимум» | Для embeddings обычно **L2-нормализация** (единичная длина); деление на max не корректно для cosine |
| «fine-tuning можно сделать после ответа» | Fine-tuning — **отдельный процесс обучения**, не шаг внутри ответа; в runtime — feedback/prompt/memory/evals |
| «RAG = внутреннее, MCP = внешнее» | Точнее: RAG — **retrieval знаний**, MCP — **tools/actions/протокол**; могут комбинироваться |
| «работает на маленькой → на большой прекрасно» | Не гарантировано; зависит от модели, chunking, metadata, reranking, данных |
| «RAG решает проблему правдивости» | Нет. Нужны citations, faithfulness-проверки, валидация ответа, контроль источников |

## 14. Цель недели (теоретическая рамка)

Тема недели по словам лектора: **научиться работать с эмбедерами, реализовать поиск по базе
знаний, включить найденное в работу агента и возвращать ссылки на источники** — как когда
просишь у ChatGPT «собери ссылки по вопросу», только теперь по **своей** базе знаний.

Главное, что должно быть понятно из теории: RAG — это **pipeline**
(`документы → chunks → embeddings → vector store → retrieval → reranking → prompt → ответ →
sources → evaluation`), а не «закинуть документы в векторную базу». Качество держится не на
одной модели, а на всех стадиях сразу.

> [`challenge-tasks.md`](./challenge-tasks.md) после публикации — здесь только теория.

## 15. Дополнения (индустриальная практика 2026, не из лекции)

### 15.1. Hybrid search

Часто используемый подход: параллельно BM25 (sparse) + dense retrieval, слияние через RRF,
сверху cross-encoder rerank. На некоторых бенчмарках даёт заметный прирост recall по сравнению
с pure dense.

### 15.2. Contextual Retrieval (Anthropic, 2024)

Перед эмбеддингом к каждому chunk дописывают короткий контекст из всего документа (50–100
токенов). В связке с hybrid и reranking снижает долю неудачных retrieval. Делается один раз на
ingestion.

### 15.3. RAGAS

Три метрики из §10 (`context relevance`, `faithfulness`, `answer correctness`) соответствуют
метрикам фреймворка RAGAS. `faithfulness` и `context relevance` можно считать reference-free;
`answer correctness` обычно требует эталона или экспертной оценки.

### 15.4. «Lost in the middle»

LLM хуже использует информацию из середины длинного контекста. Это один из аргументов за
reranking и малый top-n.
